# Synthetic input fidelity and SDK privacy compatibility

These tests use public synthetic credentials and an isolated test-only Android package. They do not use real accounts, the original computer-input controller or a physical phone. Existing public Android3.3.1 account acceptance remains scoped to its exact original APK.

The exact Flet1.1.2 Python and Dart field paths forward `enableIMEPersonalizedLearning=false`. Flutter3.47.9 revision `c197ca5199e9ee5661e865596c9c07294dfab51c` omits that field in `_AutofillScopeTextInputConfiguration`, replacing it with the default `true`. The local compatibility patch forwards this one field, retaining AutofillGroup, password masking/reveal and no-suggestion options. It is not the complete still-open [upstream PR192480](https://github.com/flutter/flutter/pull/192480), and does not establish the cause of the separate CUA bulk-input observation.

The reviewed framework file SHA-256 changes from `943aded5e35ede66a0119ff21b821921cf060b6eb8efa014b6a54333932348fe` to `34b57e5153642fcf4f4dc47b57e44ceb60f5affb3f5ca349b061aad421fe265f`. [Pinned patch, source provenance and BSD license](../packaging/flutter/README.md). Build entries fail closed on SDK selection/revision/hash/license; ordinary candidate reuse includes the build workflow and recipe. Normal post-build evidence binds generated SDK root, resolved lock, APK, workflow and policy hashes. This binding is not itself native privacy proof for a signed APK.
